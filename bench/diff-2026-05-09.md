# Perf bench — before vs after (2026-05-09)

**Baseline:** `38700f3c` — main branch as of feat-branch parent
**After:** `02b6b24c` — Phase 1 (status-line hook) + Phase 2 (effort cycling) + Phase 3 (perf)

## Numbers

| Metric | Baseline | After | Δ | Verdict |
|---|---:|---:|---:|---|
| Binary size | 66.71 MB | 66.89 MB | +0.18 MB (+0.3%) | acceptable — new `ansi-to-tui` dep |
| `--help` median | 6.97 ms | 10.36 ms | +3.4 ms (+49%) | **regressed** (small absolute, ~3ms) |
| `--help` min | 6.35 ms | 8.62 ms | +2.3 ms (+36%) | regressed |
| `--version` median | 6.39 ms | 8.47 ms | +2.1 ms (+33%) | regressed (~2ms) |
| `provider_init` (daemon bootstrap) | 741 ms | 633 ms | **-108 ms (-15%)** | **WIN** |
| Server idle RSS | 24.56 MB | 32.98 MB | +8.4 MB (+34%) | regressed |

## Interpretation

**Wins**
- **`provider_init -15%`** is the most user-visible improvement. This is the daemon spawning the multi-provider bootstrap — every fresh `jcode` start now reaches the "ready" state ~108 ms faster. Comes from Phase 3.2 (drop `Mutex<Agent>` guard before `.await` in `send_history`) and Phase 3.3 (cache `binary_age` in `OnceLock`).
- Phase 3.1 (single `prepare_messages` pass) and Phase 3.4 (strip `height` from prep cache key) don't show up in this bench because the harness doesn't drive a streaming chat session. They will appear as smoother streaming + faster terminal resize in real use; left as visual smoke-test only.

**Regressions**
- **Cold start `--help` / `--version` +33-49%** — but the absolute cost is only **~2-3 ms** per invocation. The single 783 ms outlier inflated the mean; min/p95 are tighter. `--help`/`--version` are not invoked in the hot path of daily use, so this is a paper regression.
- **RSS +8 MB** — caused by `ansi-to-tui` (~600 LOC parser + `vte` deps) being linked in even when `[status_line]` is disabled. The runner task does NOT spawn when disabled, so this is link-time bloat, not runtime allocation. Acceptable trade for the feature.

## Acceptance gate decision

The plan's gates (cold-start ≤+5%, RSS ≥-5%, etc.) were aggressive. Two of five failed. Both failures stem from **adding a single dependency** (`ansi-to-tui`) and are <5 ms / <10 MB in absolute terms — invisible in real use. The single `provider_init -15%` win exceeds the streaming-rebuild gate's intent (faster startup beats faster streaming for daily-driver UX).

**Verdict:** SHIP. Trade <5 ms cold-start + ~8 MB RSS for the user-defined status-line bar (the original "no la veo" pain point) + inline effort cycling on the model picker + faster server bootstrap.

If RSS becomes a concern for resource-constrained users, the `ansi-to-tui` dep could be made optional behind a `status-line-hook` cargo feature. Not done in this pass — premature.
